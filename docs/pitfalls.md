# 踩坑记录

这个项目里绝大多数时间花在**和文档/直觉不一致的现实较劲**上。本文把踩过的坑
按主题整理：每条给出**现象 → 根因 → 怎么办**。

用途：动手之前扫一遍，能省掉重复踩；出问题时看文末的「症状速查」。

> 未修复的缺陷不在这里，在 [`known-issues.md`](known-issues.md)。
> 本文记的是**已经解决或已经知道怎么绕**的坑。

---

## 1. 显示

### 1.1 ST7789P3 不吃通用初始化序列

**现象**：屏幕点不亮，或者显示花屏/负片/偏移。

**根因**：这块屏虽然叫 ST7789，但需要**面板厂给的专属初始化序列**
（PORCTRL / GCTRL / VCOMS / LCMCTRL / PWCTRL / 正负伽马，共 13 条命令），
不是 ST7789 的通用默认值。另外它**出厂即需反色**（无条件发 `0x21 INVON`）。

**怎么办**：序列原文在 `upstream/components/bsp/src/bsp_display.c`，
本仓库的移植版在 `os/passport/display.py` 的 `VENDOR_INIT`。**逐条照抄，不要"优化"。**
其中 `0xD0` 连发两次（第二次覆盖第一次）是参考例程的原样，别删。

### 1.2 刷完别的固件后屏幕还显示旧画面

**现象**：烧了新固件，屏幕仍显示之前的内容，像是"卡住了"。

**根因**：ST7789 的 GRAM 有残留，而新固件的写入没生效（通常是因为初始化序列不完整）。

**怎么办**：先确认初始化序列正确；确认后断电再上电。别把 GRAM 残留误判成"屏幕驱动好了"。

### 1.3 整屏 framebuf 放不下

**现象**：想用一个 240×320 的 `framebuf` 做双缓冲，直接 `MemoryError`。

**根因**：240×320×2 字节 = **153,600 字节**，而 ESP32-C3 **没有 PSRAM**，
MicroPython 可用堆只有 100~150 KB。

**怎么办**：不要整屏缓冲。纯色块按扫描线推送（只占一条线的内存），
文字用小块 framebuf 渲染后 `blit`。见 `os/passport/display.py`。

### 1.4 绘制 API 里的字节序

**现象**：颜色全反/错乱。

**根因**：MicroPython 的 `framebuf` RGB565 是**小端**存放，而 ST7789 要**高位在前**。

**怎么办**：推送前做一次 16 bit 字节翻转。见 `os/passport/display.py` 的 `_to_be()`。

## 2. 音频

### 2.1 `array.byteswap()` 在 MicroPython 里不存在

**现象**：**电脑上单元测试全绿，一烧到真机就**
`AttributeError: 'array' object has no attribute 'byteswap'`。

**根因**：`byteswap()` 是 CPython 有、MicroPython **没有**的方法。
纯 Python 逻辑测试完全暴露不出来。

**怎么办**：手写字节翻转（`display._to_be`）。并且为此加了
`tools/lint_micropython.py`，静态拦截这类"CPython 有、MicroPython 没有"的 API。

> **这类坑是本文里最危险的一种**：测试环境比目标环境"更强大"，于是假绿灯。

### 2.2 `machine.I2S` 的 `mck` 参数（已定论：ESP32 端口不支持）

**现象**：传 `mck=Pin(6)` 报 `TypeError: extra keyword arguments given`。

**根因**：**官方文档与 ESP32 端口的实现不一致。**

- 文档（v1.29.0）写的是通用签名
  `machine.I2S(id, *, sck, ws, sd, mck=None, mode, bits, format, rate, ibuf)`，
  里面确实有 `mck`；
- 但 **ESP32 端口的实现里根本没有这个参数** ——
  `ports/esp32/machine_i2s.c`（tag `v1.29.0`）全文**没有出现过 `mck`**。

真机复测（2026-09-19，MicroPython v1.29.0 on ESP32-C3）把四种写法都试了：

| 写法 | 结果 |
| --- | --- |
| `mck=Pin(6)` | `TypeError: extra keyword arguments given` |
| `mck=6`（整数） | 同上 |
| **`mck=None`** | **同上** |
| 其余参数（sck/ws/sd/mode/bits/format/rate/ibuf） | 全部接受 |

`mck=None` 也被拒是决定性证据：如果它是被识别的关键字，传文档默认值不该报错。
所以这不是"参数值不对"，而是**该端口没有解析这个名字**。

**怎么办**：走 ES8311 的 **BCLK 倍频**（`use_mclk=False`，官方驱动里本就有的分支），
本项目的音频就是这么做的，真机出声正常。想在 GPIO6 上出 MCLK 只能用 ESP-IDF。

> **教训**：MicroPython 的文档是按"通用 API"写的，**具体端口可以少实现参数**。
> 遇到 `extra keyword arguments given` 时，除了查文档，也要查
> `ports/<端口>/` 下的对应 C 源码 —— 以真机行为为准。
> （本条曾一度被记为"可能是误诊"，后经源码 + `mck=None` 两项证据确认为真。）

### 2.3 想录音，但 I2S 被系统占着

**现象**：小程序里 `I2S(0, ...)` 建不起来，或者建起来了但没声音。

**根因**：PassportOS 启动时已经把 `I2S(0)` 用来播放了。**一个 I2S 外设只能有一个实例**，
而 MicroPython 又做不到"两个实例共享时钟"。

**怎么办**：**做交接** —— 先 `ctx.audio.deinit()` 把播放实例关掉，
再用同一组 BCLK/WS、换数据脚（DIN）建 RX；录完 `deinit` RX，重建 `Audio()` 播放。
完整实现见 [`../miniapps/repeater.py`](../miniapps/repeater.py)。

⚠ 副作用：你 `deinit` 掉的是**系统共享的** `ctx.audio`，退出前要还一个新的
`Audio()` 回 `ctx.shell.audio`，否则别的程序（如 Sound）会发现音频死了。

### 2.4 录音缓冲：一个大 `bytearray` 要不到

**现象**：`bytearray(64000)` 抛 `MemoryError`，但系统显示"还有 60 KB 可用"。

**根因**：MicroPython 的 GC 堆是**碎片化**的。"最大连续可分配块"远小于"总空闲"。
实测：总空闲够，但单一 64 KB 块拿不到，退让阶梯一路跌到 16 KB（只够 0.5 秒）。

**怎么办**：**分配成一串小块**（比如每块 8 KB），能拿几块拿几块，播放时按顺序逐块喂 I2S。
同一条件下，单块方案拿 12 KB，分片方案能拿 60 KB。

### 2.5 `ESP_ERR_NO_MEM`：I2S 的 DMA 内存必须先拿

**现象**：建 I2S 时报 `OSError: ESP_ERR_NO_MEM`。

**根因**：**注意这是 ESP-IDF 的错，不是 MicroPython 的 `MemoryError`** —— 两者来自
不同的分配器。I2S 的 DMA 缓冲需要**连续的内部 RAM**，被 MicroPython 的堆吃掉之后就没了。
原版代码先把 64 KB 录音缓冲吃掉，再去建 I2S，必然失败。

**怎么办**：**先建 I2S，再分配录音缓冲**。再加一层：万一还是建不起来，
就吐出一片缓冲给 DMA 用，重试。

### 2.6 `play_raw()` 会冻结整个主循环

**现象**：播放期间按任何键都没反应；偶尔"按住才有用"。

**根因**：`play_raw()` 把整段音频一次性交给 I2S，而 DMA 缓冲只有 2 KB ——
CPU 要干等 DMA 吐完，**整个播放期间主循环是冻结的**：按键根本不采样，
那一按**压根没被读到**。"按住偶尔有效"是因为播放结束后 `update()` 恢复，
而它要求连续两次读到同一状态才算一次按下。

**怎么办**：**分片喂**。每次只调一次 `play_raw(512 字节)`，然后返回主循环。
实测一轮播放从"1 次 `loop()` 阻塞 1.8 秒"变成 **57 次 `loop()`**，且 DMA 一直是满的、不断音。

### 2.7 `tone()` 的时长与阻塞

**现象**：放一段"长音"直接 `MemoryError`；或者放音期间界面卡住。

**根因**：`tone(freq, ms)` 按**整段时长一次性分配**缓冲：16 kHz × `ms` × 2 字节。
可用堆约 110 KB，所以 `ms` 超过约 3000 就没了。而且波形是纯 Python 逐样本生成的。

**怎么办**：单次音长控制在约 1 秒内。需要更长的声音就自己切片循环调用。

## 3. 蓝牙

### 3.1 GATT 特征值默认只有 20 字节，超长写入被**静默截断** ⭐

**现象**：能连上、能握手，**就是一推送就报"命令不是合法 JSON"**。

**根因**：MicroPython 的 GATT 特征值默认最大长度只有 **20 字节**
（= 默认 ATT MTU 23 − 3）。超过的写入被**静默截断**，设备收到半截 JSON。
实测：客户端写 69 字节，设备只收到 20 字节。而 `put` 命令约 48 字节，**必然中招**。

**怎么办**：**显式放大特征值缓冲**：
```python
ble.gatts_set_buffer(cmd_handle, C.BLE_ATTR_MAX_LEN, False)   # 2048
```
MicroPython **不会给任何提示**，必须自己设。

> 这是整个项目最坑的一个问题：错误现象（"JSON 不合法"）和根因（特征值缓冲）
> 之间没有任何线索。

### 3.2 Windows 会缓存 GATT 服务表

**现象**：设备改过特征值之后，Windows 侧报
`Characteristic ... was not found`，而设备日志明确显示两个特征值都注册成功。

**根因**：Windows 缓存了旧的 GATT 服务表。

**怎么办**：`bleak` 里传 `winrt=WinRTClientArgs(use_cached_services=False)`
（`tools/ble_*` 已默认启用）。浏览器端遇到同样症状，到
「设置 → 蓝牙和其他设备」删掉设备再连。

### 3.3 中心设备抓着链路不放，设备不再广播

**现象**：客户端断开后，**再也扫不到设备了**，只能重启设备。

**根因**：实测中心设备（Windows）在客户端调用 `disconnect()` 之后**仍然抓着 BLE 链路**，
设备侧一分钟都收不到断开事件 —— 期间不广播。

**怎么办**：两层防御：
1. 客户端收尾时**先发 `{"t":"bye"}`**，由**设备端主动断开**；
2. 设备端另有 **25 秒空闲看门狗**兜底（崩溃/关标签页来不及说再见的情况）。

### 3.4 上传超过 10 秒，心跳会被写进源码 ⭐

**现象**：推送显示"完成"，但小程序运行不起来 / 报 `UnicodeError` / 报语法错误。

**根因**：手机端每 10 秒发一次心跳 `{"t":"ping"}` 给看门狗续命，而**上传期间没停**。
设备在数据模式下只把 `abort`/`end`/`put`/`stop` 识别为控制命令，`ping` 不在其中 ——
于是这 12 字节被**当成源码写进 `app.py`**，同时让设备**提前 12 字节**认为收满，
**末尾 12 字节真实源码被丢弃**。而设备照常回 `done`。

**怎么办（临时）**：**推之前先断开再重连，然后立刻推** —— 心跳是连接后第 10 秒
才第一次触发的，只要"连接 → 传完"在 10 秒内就安全。另外**文件越小越安全**。

**怎么办（根治）**：需要改代码，见 [`known-issues.md`](known-issues.md) #1。

### 3.5 源码里的非 ASCII 会把错误变得更难懂

**现象**：加载小程序时报 `UnicodeError`，屏幕显示 `LOAD FAILED`。

**根因**：`apps.read_source()` 用**文本模式** `open()`，按 UTF-8 解码。
如果上传被截断（见 3.4）而切点正好落在**一个多字节字符中间**，文件就成了非法 UTF-8。

**怎么办**：**小程序源码只用 ASCII**。这样即使被截断，也**只可能是普通语法错误**，
不会是难以理解的 `UnicodeError`。这条已由 `tools/check_docs.py` 强制检查。

### 3.6 手机端一次只能选一个文件

**现象**：想一次推多个小程序，发现文件选择框不能多选。

**根因**：`pwa/index.html` 的 `<input type="file">` 没有 `multiple`，且代码只用 `files[0]`。

**怎么办**：三选一 ——
① 用 [`../miniapps/_bundle.py`](../miniapps/_bundle.py) 打成安装包，推一次装多个；
② 在电脑上用 `tools/ble_client.py push` 写个循环；
③ 把小程序放进 `os/builtin/` 再 `deploy.py`，让它随系统发布。

## 4. 内存与性能

### 4.1 把堆吃光会让**整个应用**变卡

**现象**：录音能吃满 4 秒，但界面卡住、进度条不动、状态文字几秒才刷一次。

**根因**：界面每画一笔都要申请小内存。**堆满之后每次申请都触发一次完整 GC**，
主循环慢到几乎不动。这不是"绘制太慢"，是"分配太贵"。

**怎么办**：**永远留一块不碰**（`RESERVE`，约 10~16 KB）。用 `gc.mem_free()` 算预算，
低于预留就停止分配。宁可少录一点，也别把系统拖死。

### 4.2 按帧号节流会在慢循环下退化

**现象**：进度条在动，但它下面的文字几秒才刷新一次。

**根因**：用 `ctx.frame % 3` / `% 15` 做节流是**按帧数**的。循环一变慢，
`% 15` 就从"每 0.3 秒"退化成"每 3 秒"—— 而 `% 3` 的进度条还能勉强跟上。
于是出现"进度条动、文字不动"的错觉。

**怎么办**：**按时间节流**：用 `time.ticks_ms()` 判断距上次刷新过了多久，
固定 10 Hz，与帧率无关。

### 4.3 报告的空闲内存 ≠ 能分配的内存

**现象**：`gc.mem_free()` 说还有 60 KB，但 `bytearray(64000)` 失败。

**根因**：碎片化（见 2.4）；而且 I2S 的 DMA 走的是**另一个分配器**，
`gc.mem_free()` 完全看不到那一边的压力。

**怎么办**：别信单一数字。分片分配 + 留预留 + 失败退让，三件事一起做。

## 5. 小程序运行时

### 5.1 长按 OK 超过 1.2 秒，系统会强制退出小程序

**根因**：`ui.py` 里 `LONG_PRESS_MS = 1200`，运行态长按 OK 就 `stop_app()`。

**怎么办**：**不要设计需要长按 OK 的交互**。"按住说话"这类玩法在小程序层做不到 ——
需要改固件放开这个限制。

### 5.2 没有"按键松开"事件

**根因**：`on_key` 只在**按下**时触发，没有释放回调。

**怎么办**：要么避免依赖"按住/松开"（改成"按一下开始、再按一下停止"，
这通常还更好用）；要么每帧轮询 `ctx.shell.buttons.current()` ——
但那是**内部字段**，将来可能变。

### 5.3 `MAX_APPS` 只在 BLE 路径强制

**现象**：App 推送说"应用数量已达上限 12"，但安装包能装更多。

**根因**：上限只在 `blepush.py` 的 `put` 里检查；小程序**直接写文件**是绕过它的。

**怎么办**：知道有这回事就行。真要突破 12 个，用安装包；
但三键翻几十个应用很难用，12 这个数不算离谱。

### 5.4 音频对象可能是 `None`

**根因**：音频初始化失败时系统照常启动，`ctx.audio` 会是 `None`。

**怎么办**：**每次用前判空**：`if ctx.audio and ctx.audio.ok:`。

## 6. 刷机与工具

### 6.1 手搓 raw REPL 会卡住并留下截断文件

**现象（历史）**：`deploy.py` 第一版用 pyserial 手搓 MicroPython 原始 REPL，
每传一个分片一次往返 —— **实测会卡住并留下截断的文件**。

**怎么办**：改用官方 **mpremote**，并**回读设备上的文件大小与本地比对**。

### 6.2 esptool v4 和 v5 的命令名不一样

v4 用下划线（`write_flash` / `erase_flash`），v5 改成连字符（`write-flash` / `erase-flash`）。
`tools/esp.py` 探测主版本后自动重写命令与取值，让 `.bat` 和文档里的命令在两个大版本下都能用。

### 6.3 `deploy.py --clean` 失败会让设备失去可启动的系统

`--clean` 会**递归删除** `/passport` 和 `/apps`，而且没有二次确认。
如果删除之后传输失败，设备上就没有可运行的系统了。**知道这个风险再用**。

### 6.4 Android 的文件系统大小写不敏感

**现象**：`git mv docs/PROTOCOL.md docs/protocol.md` 报告成功，但文件名**没变**。

**根因**：sdcard 之类的位置是**大小写不敏感**的，仅大小写不同的改名等于没改。

**怎么办**：改成真正不同的名字（本项目最终用了 `ble-protocol.md`），
或者用"先改成临时名、再改成目标名"两步走。

## 7. 开发方法（写给未来的自己）

### 7.1 `py_compile` 通过 ≠ 能在设备上跑

**这一轮写 5 个小程序，静态检查全过，但校验器抓出 3 个会上板就崩的错**：

| 错误 | 后果 |
| --- | --- |
| 引用了**不存在的模块级 `ctx`** | `NameError`，一调用就崩 |
| `setup()` 里**先画界面、后初始化状态** | `AttributeError` |
| `onKey` 里**少传一个函数参数** | `TypeError` |

**教训**：写完必须**空跑一遍**。为此写了
[`../miniapps/_verify.py`](../miniapps/_verify.py)：桩件跑 `setup/loop/on_key/teardown`，
查绘制越界、注入按键序列、报告异常行号。

### 7.2 假绿灯比红灯危险 —— 三次自己骗自己

写校验器时我三次得出**错误结论**，都是测试代码的问题：

| 假象 | 真相 |
| --- | --- |
| "RESERVE 全部击穿 ❌" | 假 `bytearray` **释放时不减计数**，账目全错 |
| 同上，第二次 | 手动把 `used` 清零，而旧对象还活着，之后回收又减一次 → 负数 |
| "RESERVE 根本没生效" | 被测文件开头有 `import gc`，**把我注入的假 `gc` 覆盖了** —— 于是 `gc.mem_free()` 读的是电脑的几百 MB 内存 |

**教训**：
- 注入桩件时，凡是**被测代码会 `import` 的模块**，必须替换 `sys.modules`，
  不能只塞进 globals（`import` 会覆盖）；
- 假的内存模型必须**在对象释放时减计数**；
- 不要用 `dict(g)` 复制命名空间后改它 —— 原函数仍指向旧的那份。

### 7.3 设备上 `/apps` 本来就存在

写文件系统沙箱测试时，忘了预建 `/apps`，导致所有 `os.mkdir("/apps/x")` 都因为
父目录不存在而失败。**真实设备上 `boot.py` 会建这个目录**，沙箱要照做。

### 7.4 两个 Agent 写同一份文档 = 系统性漂移

这个仓库的文档曾经由两个不同的 Agent 分别生成，结果是：

- 音频模块**已实现并真机验证出声**，却有三份文档写着"未实现"
- 示例小程序从 3 个变成 4 个，多份文档没跟
